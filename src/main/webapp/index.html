What the application does

A small, believable product rather than a template site: one workflow for students, one for administrators, both driven by the same database.

1

Registration & sessions

Sign-up with duplicate-email detection, BCrypt password hashing, session-based login and a role stored in the session.

2

MCQ attempt screen

Question navigator, answered / unanswered states, optional countdown timer and a confirmation step before submitting.

3

Server-side scoring

The browser posts only the chosen letters. The score, percentage and pass state are computed in Java from the stored answer key.

4

Result review

Question-by-question feedback: what the student chose, the correct option and an optional explanation, with unanswered rows kept distinct.

5

Admin management

Create and edit quizzes, add or remove questions with four options each, publish when ready, and browse users and results.

6

Safe data access

Every query uses PreparedStatement, connections come from a small pool, and quiz submission is wrapped in a single transaction.

Architecture

A straightforward layered design: the servlet handles HTTP, the service holds the business rules, the DAO owns the SQL. No framework hides the Java work.

Database schema

usersid, name, email, password_hash, role
quizzestitle, description, category, duration_min, status
questionsquiz_id → quizzes, question_text, correct_option
question_optionsquestion_id → questions, option_key, option_text
attemptsuser_id, quiz_id, score, percentage, submitted_at
answersattempt_id, question_id, selected_option, is_correct

One user → many attempts. One quiz → many questions. One question → four options. Foreign keys cascade on delete.

How a submission is scored

The full round trip, which is what a viva will ask about.

  1. Student clicks Submit; the form posts q_12=B style fields only.
  2. AuthFilter confirms a session exists and that the route is allowed.
  3. SubmitQuizServlet collects the letters into a Map<Long, Character>.
  4. ResultService reads the answer key from MySQL and compares.
  5. Score and percentage are computed in Java with floating-point division.
  6. AttemptDAO writes the attempt and all answers in one transaction, then commits.
  7. The servlet redirects to the result page (POST / Redirect / GET).

What the browser never receives

The attempt screen is rendered from copies of the questions with the correct answer and explanation stripped out, so the answer key simply is not present in the page source.

POST /quiz/submit quizId=1 q_1=B q_2=C q_3=D … (no score field exists)

Running the real build

  1. Install JDK 17, MySQL 8 and Tomcat 10.1
  2. Run sql/schema.sql, then sql/seed.sql
  3. Copy db.properties.example to db.properties
  4. Run mvn clean package
  5. Deploy target/quizdesk.war to Tomcat
  6. Open http://localhost:8080/quizdesk/
